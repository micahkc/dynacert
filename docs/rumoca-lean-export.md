# rumoca → Lean export: proposed contract

This is a draft. It describes what dynacert expects from rumoca's Lean backend, starting with
the explicit-ODE subset. The rumoca emitter is part of the **trusted base**: dynacert's
theorems are about the Lean `system`, so the export should be a direct, readable transcription
of the flattened equations. Any simplification belongs on the dynacert side, where it can be
checked with a proof.

## Supported subset (v0)

- Flattened, index-reduced model in explicit form `der(x) = f(x, w)`. No algebraic loops,
  `when`/events, or `pre()`.
- Real-valued states only, with parameters fixed at their declared values.
- Each `input` is either a **disturbance** (bounded, universally quantified in the theorem) or
  must be eliminated (closed loop) before export. The disturbance list could come from
  `uncertainty.yaml`, as in cp_reach, or from a Modelica annotation.

## Emitted module

One Lean file per model, for example `Dynacert/Examples/MassSpringDamper/Model.lean`:

```lean
import Dynacert.Core.System

/-! # MassSpringDamper (generated by rumoca <version> from closed_loop.mo) -/

namespace Dynacert.Examples.MassSpringDamper.Model

open Dynacert

-- Parameters, as exact rationals (decimal literals converted exactly: 0.2 ↦ 1/5)
def m : ℚ := 1
def c : ℚ := 1/5

-- Ordering metadata, used by tooling and in messages only
def stateNames : List String := ["e", "ev"]          -- x 0, x 1
def disturbanceNames : List String := ["d"]          -- w 0

/-- der(e) = ev;  der(ev) = (d - c*ev - k*e - kp*e - kd*ev) / m -/
noncomputable def system : System 2 1 where
  f x w := ![x 1, ((w 0 : ℝ) - c * x 1 - k * x 0 - kp * x 0 - kd * x 1) / m]

end Dynacert.Examples.MassSpringDamper.Model
```

### Conventions

- **State vector** `x : Fin n → ℝ`, **disturbance** `w : Fin m → ℝ`. Their order follows
  `stateNames` / `disturbanceNames`.
- **Parameters** are `def p : ℚ` and are cast to `ℝ` automatically inside `f`. Exact rationals
  keep certificate checking in exact arithmetic.
- **Expressions**: `+ - * /`, natural-number powers `x ^ 2`, and for nonlinear models
  `Real.sin`, `Real.cos`, `Real.exp`, `Real.sqrt`, `Real.arctan`. Keep the expression structure
  of the source (no CSE or reordering) so the output can be audited against the `.mo` file.
- **Namespace** follows the module path. dynacert's generated `Cert.lean` imports the module
  and refers to `system`.

## Sidecar for the oracle

The oracle needs the same model numerically (A, B or Jacobians). rumoca should emit the
existing JSON IR from the **same** flattened model. If the two disagree, nothing unsound
happens: the certificate simply fails to check against `system`.

## Current state in dynacert

- `Model.lean` in the example is written by hand in this format. It also contains `model`
  (the LTI form) and `model_toSystem`, a proof that the LTI form matches `system`. That part
  will move into the oracle-generated file, so rumoca only has to emit `system`.
- The example uses tracking-error coordinates, derived by hand from `closed_loop.mo`.
  Eventually rumoca should export the full closed-loop model, and the change to error
  coordinates should be done (and proved) in Lean.
